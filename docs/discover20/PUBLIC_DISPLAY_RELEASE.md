## Close refresh and rule-based calendar (since 2026-11-03)

The October release bound freshness to a calendar hard-coded to 2026-10-01..2026-10-30. After it expired on 31.10.2026 the session proof correctly failed closed and every Europe route showed "Europa noch nicht verfügbar".

- **Calendar.** `core/europe-exchange-calendar.js` derives exact-MIC sessions for any date from a weekday rule plus each venue's recurring holidays and early closes (XETR, XPAR, XAMS, XBRU, XMIL, XMAD, XSWX, XSTO, XCSE, XWBO). It reproduces the reviewed exchange_calendars 4.13.2 October 2026 schedule exactly (pinned hash in `core/tests/europe-discover-refresh.test.mjs`), and the producer refuses to run unless it also reproduces every published 1Y display window of the baseline. The published window is derived from the oldest last observation and the run date (`publicationWindow`: 35 days before, 120 days after); no source file may contain a fixed calendar date (test). Unscheduled one-off closures cannot be predicted and appear as missing sessions, never as prices.
- **Refresh.** `node scripts/marketstack/europe-discover-publication.mjs refresh` (workflow `europe-discover-refresh.yml`, manual or daily at 17:47 UTC while the repository variable `EUROPE_REFRESH_SCHEDULE_ENABLED` is `true`) verifies the full manifest hash chain, sends one bounded Marketstack `/eod` request per primary listing (449 requests / 449 conservatively reserved credits; cap 600 by default, hard cap 1,000), and appends only observations that pass the unchanged Close evaluator and match the published overlap close. Existing prices, quarantines, identity and exclusion proofs stay unchanged; conflicts hold that listing at its previous data, which the unchanged freshness gate then blocks. Provider RAW stays in the runner's private temp directory and is deleted; only response hashes enter the public evidence chain. Long-history display windows are extended by the appended tail only and can never improve their previous status. Known-invalid provider symbols (the last real request was answered with HTTP 422 `no_valid_symbols_provided`, recorded in `refresh.held` and the hash-bound `publication.blocked`) are not requested again: they stay BLOCKED with the same reason class and code, are listed with `lastProbedAt` in `refresh.preExcluded`, and still count towards the 22-blocked limit. Only a manual dispatch with `reprobe_known_invalid=true` requests them again; a deterministic 422 is never retried within a run.
- **Freshness is unchanged.** Lag 0 current, 1 delayed, 2–3 limited, >3 blocked. Without a further run the data turn stale after three completed sessions; a refresh schedule needs a separate owner decision (about 449 reserved credits per run).
